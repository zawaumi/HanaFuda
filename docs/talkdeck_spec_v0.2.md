# TalkDeck MVP仕様書 v0.2

- 更新日: 2026-09-20
- ステータス: 3人チーム開発用の合意版
- 参照元: `talkdeck_spec_v0.1.md`、会話デッキのモック

## 1. プロダクト定義

### 一言で表すと

**相手との関係や過去の会話を踏まえ、次に何を話すかを準備してくれるAI会話デッキ。**

### 解決する課題

- 初対面や久しぶりに会う相手との話題が思いつかない
- 相手について以前聞いたことを忘れる
- 汎用チャットAIへ毎回状況を説明するのが面倒
- 会話への心理的ハードルが高い

### MVPの価値

ユーザーは相手と今回の状況を入力するだけで、すぐ口に出せる話題と会話の分岐を得られる。会話後の短い記録は、同じ相手との次回デッキへ引き継がれる。

## 2. 想定ユーザー

メインターゲットは、初対面・雑談・交流に苦手意識がある大学生。ハッカソン、大学、サークル、1on1、交流会などの対面会話を主な利用場面とする。

## 3. MVPスコープ

### 必須

1. 自分のプロフィールを登録・編集できる
2. 会話相手を登録・一覧・検索できる
3. 相手のプロフィールと記憶を確認できる
4. 相手、目的、状況、補足情報を指定できる
5. AIが会話デッキを生成できる
6. デッキに3〜5枚の話題カードを表示できる
7. 各カードに話し始め方と、返答に応じた分岐を表示できる
8. 会話後に評価とメモを記録できる
9. 会話履歴と新しい記憶を相手ごとに保持できる
10. 過去の記録を次回のデッキ生成に利用できる

### モックを受けて追加する機能

- 相手を登録しない「さくっと話題」生成
- つながり一覧のキーワード検索
- 相手詳細から直接「次の話題」を作る導線
- デッキの再生成
- PCのサイドナビとモバイルの下部ナビ

### MVP対象外

- Google Calendar連携
- SNS・URLからのプロフィール自動取得
- 音声認識、会話中のリアルタイム提案
- メール、チャット、電話向けモード
- 複数LLMの自動切り替え
- 会話全文の録音・保存

## 4. 基本ユーザーフロー

```text
ホーム
  ├─ 初めて会う人を登録
  │    └─ 会話設定 → 生成中 → デッキ → 会話記録 → ホーム
  ├─ 最近話した人を選択
  │    └─ 会話設定 → 生成中 → デッキ → 会話記録 → ホーム
  └─ さくっと話題
       └─ ランダムな汎用話題を3件表示

つながり
  ├─ 検索
  ├─ 相手詳細
  └─ 次の話題 → 会話設定

会話履歴
  └─ 日付、相手、評価、話題、新しく記録したことを表示
```

## 5. 画面一覧

| 画面 | 主な役割 | 主な操作 |
|---|---|---|
| ホーム | 次の会話準備を始める | 新規相手登録、最近の相手を選択、さくっと話題 |
| つながり一覧 | 登録済みの相手を探す | 検索、詳細表示、デッキ作成 |
| 相手詳細 | 相手との関係と記憶を確認する | 次のデッキ作成 |
| 自分のプロフィール | AIが参照する自分の情報を管理する | 所属、興味、最近の活動、避けたい話題を編集 |
| 相手登録 | 初対面の相手を最低限登録する | 名前、関係、既知情報、会う状況を入力 |
| 会話設定 | 今回の会話条件を入力する | 目的、状況、相手の情報、補足を入力 |
| 生成中 | AI処理中であることを示す | 状況メッセージを表示 |
| デッキ | 話題をおすすめ順に表示する | 分岐を開く、再生成、記録へ進む |
| 会話記録 | 会話結果を残す | 3段階評価、任意メモを保存 |
| 会話履歴 | 過去の会話を振り返る | 履歴一覧を確認 |

## 6. 会話デッキ仕様

### カード数

1回の生成につき3〜5枚。上からおすすめ順に並べ、先頭カードを「いちばん自然」として強調する。

### カード項目

```json
{
  "topic": "話題名",
  "starter": "そのまま口に出せる話し始め方",
  "reason": "この話題を勧める理由",
  "branches": [
    {
      "condition": "相手の返答・反応",
      "next": "次に聞くこと"
    }
  ]
}
```

`reason` は生成・保存対象だが、初期表示では隠してよい。分岐はカード内で展開する。

### 生成ルール

- 自然な短い日本語にする
- 面接のような質問攻めにしない
- 共通点、現在の状況、過去の会話を優先する
- 「避けたい話題」に該当する内容を出さない
- 過去の話題を使う場合は、単純な繰り返しではなく続きとして提案する
- JSON以外を返さない

## 7. データモデル

### User

- `id`
- `name`
- `status`：所属・立場
- `interests`：興味
- `recent`：最近の活動
- `avoid_topics`：避けたい話題
- `created_at` / `updated_at`

### Person

- `id`
- `user_id`
- `name`
- `relationship`
- `known_information`
- `created_at` / `updated_at`

### Conversation

- `id`
- `person_id`
- `purpose`
- `situation`
- `extra`
- `rating`：`good` / `normal` / `poor`
- `memo`
- `created_at`

### Deck

- `id`
- `conversation_id`
- `summary`
- `cards`：JSON
- `created_at`

### PersonMemory

- `id`
- `person_id`
- `content`
- `source_conversation_id`
- `confirmed`：ユーザー確認済みか
- `created_at`

## 8. API契約

バックエンドはFastAPIで実装する。フロントエンドはバックエンドの内部実装やDBへ直接依存せず、以下のHTTP APIだけを境界とする。

| Method | Path | 用途 |
|---|---|---|
| `POST` | `/api/deck/generate` | 会話デッキ生成 |
| `GET` | `/api/persons` | 相手一覧・検索 |
| `POST` | `/api/persons` | 相手登録 |
| `GET` | `/api/persons/{person_id}` | 相手詳細 |
| `PATCH` | `/api/persons/{person_id}` | 相手情報更新 |
| `GET` | `/api/conversations` | 会話履歴一覧 |
| `POST` | `/api/conversations` | 会話結果の保存 |
| `POST` | `/api/persons/{person_id}/memories` | 確認済み記憶の保存 |
| `GET` / `PATCH` | `/api/profile` | 自分のプロフィール取得・更新 |

### デッキ生成リクエスト

```json
{
  "user": {},
  "person": {},
  "context": {
    "purpose": "特に目的はない",
    "situation": "ハッカソン会場で初めて会う",
    "extra": ""
  },
  "history": []
}
```

### デッキ生成レスポンス

```json
{
  "summary": "短いアドバイス",
  "cards": []
}
```

### API共通方針

- JSONのキー名はsnake_caseで統一する
- FastAPI側はOpenAPIを正とし、フロントエンドは型を合わせる
- 成功時は2xx、入力不正は422、未認証は401、対象なしは404、サーバー障害は5xxを返す
- エラー本文は最低限 `detail` を持つ
- CORSの許可元は環境変数で設定する

## 9. 技術・ディレクトリ方針

```text
HanaFuda/
├─ frontend/   # フロントエンド担当の作業範囲
├─ backend/    # バックエンド担当の作業範囲
└─ docs/       # 共有仕様、API契約、意思決定
```

- フロントエンド: Next.js / React / Tailwind CSS
- バックエンド: FastAPI
- DB・認証: Supabase PostgreSQL / Supabase Auth
- LLM: OrcaRouter経由。モデル名はバックエンドの環境変数で切り替える
- `frontend` と `backend` は依存関係、環境変数、起動手順を完全に分離する
- APIキーとLLM呼び出しはバックエンドだけが扱い、ブラウザへ渡さない
- フロントエンドはAPIのベースURLを環境変数で受け取る

## 10. 担当境界

### フロントエンド担当

- `frontend/` 配下のみを実装する
- 画面、フォーム、レスポンシブ、状態管理、APIクライアントを担当する
- バックエンド未完成時は、合意したAPIレスポンスと同形のモックデータを使う
- API仕様の不一致はコードで吸収せず、`docs/` またはIssueで合意する

### バックエンド担当

- `backend/` 配下のみを実装する
- FastAPI、Supabase、認証、履歴・記憶保存、LLM連携を担当する
- OpenAPIと実際のレスポンスを一致させる

### 共通ルール

- フロントエンド担当は `backend/` を変更しない
- バックエンド担当は `frontend/` を変更しない
- 共有仕様の変更は `docs/` の更新を含むPRで行う
- 結合点はHTTP APIとJSON形式だけに限定する

## 11. UI方針

- モバイルファーストで、会う直前に短時間で使えることを優先する
- PCは左サイドナビ、モバイルは下部ナビを使用する
- ナビゲーションは「ホーム」「つながり」「会話履歴」の3項目
- デッキは長文を避け、最初に話題名と話し始め方だけを見せる
- 主要操作は1画面1つを基本とする
- 読み込み中、生成失敗、保存成功を明確に伝える

## 12. モックとv0.1の差分・決定

| 論点 | v0.2での決定 |
|---|---|
| 画面数 | v0.1の6画面想定から、モックに合わせて10画面相当へ整理 |
| ナビゲーション | ホーム、つながり、会話履歴の3項目で固定 |
| 初対面 | 名前が分からなくても登録でき、そのまま会話設定へ進める |
| 汎用話題 | 相手登録なしで3件表示する「さくっと話題」をMVPへ追加 |
| 人物検索 | 名前・メモ・タグ相当のキーワード検索をMVPへ追加 |
| カード枚数 | 固定3枚ではなく3〜5枚。UIは返却件数に追従 |
| フィードバック | 3段階評価と任意メモに限定 |
| 記憶更新 | AIが候補を抽出し、ユーザー確認後に保存する |
| 永続化 | モックの固定データ・画面内状態からSupabase保存へ置換する |
| バックエンド | Next.js APIではなくFastAPIを採用 |
| リポジトリ構成 | `frontend/` と `backend/` を完全分離 |

## 13. 完了条件

次の一連の操作が実データで完走すればMVP完成とする。

1. ユーザーがプロフィールを保存できる
2. 相手を登録できる
3. 会話条件を入力し、5秒程度を目標にデッキを生成できる
4. 3〜5枚のカードと分岐を確認できる
5. 会話後の評価とメモを保存できる
6. 保存内容が会話履歴と相手詳細に反映される
7. 同じ相手で再生成した際、過去の記録が入力に含まれる
8. スマートフォン幅で主要操作が問題なく行える
9. `frontend/` と `backend/` を個別に起動でき、環境変数も分離されている

## 14. 実装前に3人で決める事項

1. 認証をハッカソンMVPに含めるか、固定デモユーザーにするか
2. AIが抽出した記憶の確認UIを、会話記録画面内に置くか別画面にするか
3. 「さくっと話題」を固定候補にするかAI生成にするか
4. LLMの本番モデルと、API障害時のデモ用フォールバック条件
5. FastAPIのベースURL、ローカルポート、CORS許可元
6. OpenAPIからフロントエンド型を自動生成するか、手動で管理するか

上記以外は本仕様を優先し、迷った場合は「会う直前に最短でデッキを開けるか」で判断する。
