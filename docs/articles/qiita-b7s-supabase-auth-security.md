たるてんです！

今回は、自分が開発しているHanaFudaというアプリのバックエンドを題材に、Supabase Authによる認証と、APIを安全にするための整理を行いました。

認証は「ログイン画面を作れば終わり」ではありません。
どのユーザーのデータを返してよいのかを、API側が毎回判断できなくてはいけません。

また、認証を追加すると処理が増えます。
そこで今回は、認証の処理で遅くなりすぎないように、データベースの取得方法も一緒に見直しました。

## なぜ認証を作ることにしたのか

HanaFudaの初期APIでは、`X-User-ID`というヘッダーにUUIDを入れてユーザーを切り替えていました。

```text
X-User-ID: 11111111-1111-1111-1111-111111111111
```

これはローカルでAPIを試すには便利です。
しかし、誰でもこのUUIDを知っている、または推測できる場合、そのユーザーになりすませてしまいます。

つまり、これは認証ではなく、デモ用の目印です。
本番でこのまま使うわけにはいきません。

## `X-User-ID`だけでは何が困るのか

APIが受け取ったユーザーIDを、そのまま「ログイン中のユーザー」として扱うとします。

このとき、攻撃者が別のUUIDを送るだけで、別の人のデータを検索できてしまう可能性があります。

データベース側でRLSを設定していても、バックエンドがserver-only keyで接続している場合、Supabase側ではそのアクセスを強い権限として扱います。

そのため、バックエンド自身が次の二つを行う必要があります。

1. 本当にログイン済みのユーザーか確認する
2. 確認できたユーザーIDを使って、すべての検索条件を絞る

## Supabase Authのアクセストークンを使う

Supabase Authでログインすると、フロントエンドはアクセストークンを受け取ります。

バックエンドには次の形式で送ります。

```http
Authorization: Bearer <access_token>
```

バックエンドはこのトークンをSupabase Authへ確認し、返ってきたユーザーIDをAPI内部で使います。

これで、リクエスト本文や任意のヘッダーに書かれたIDを信用せずに済みます。

本番では、Bearer tokenがないリクエストを401で拒否します。
一方、フロントエンドの認証画面がまだ作られていない開発中だけは、`AUTH_MODE=legacy`を明示して従来の`X-User-ID`を利用できます。

大事なのは、互換モードを用意することではなく、互換モードを本番へ持ち込まないことです。

## server-only keyとユーザーのトークンは別物

ここで少し混乱しやすいものがあります。

- server-only key: バックエンドがSupabaseへ接続するための秘密鍵
- access token: ログインしたユーザーを表す短期のトークン

server-only keyは、ブラウザへ渡してはいけません。
Git管理にも入れてはいけません。

一方、ユーザーのaccess tokenは、ブラウザからAPIへ送ります。
ただし、API側で検証してからユーザーIDとして使う必要があります。

この二つを同じものとして扱うと、権限設計が崩れてしまいます。

## 速くするために、まず取得件数を制限する

次にパフォーマンスを見直しました。

一覧APIがデータを無制限に返す設計だと、データが増えたときに次の問題が起きます。

- Supabaseから大量の行を取得する
- APIレスポンスが大きくなる
- フロントエンドの描画が重くなる
- 認証や通信の待ち時間が目立つ

そこで、相手一覧、会話一覧、記憶一覧には、1〜100件の`limit`を設定しました。

最初から完全なページングを作るのではなく、まず無制限取得を止めることにしました。
これは地味ですが、事故を小さくするために効果があります。

## インデックスと短いキャッシュ

データベースには、よく使う検索条件に合わせて複合インデックスを追加しました。

例えば会話履歴なら、ユーザー、相手、作成日時の順に検索します。

```sql
create index if not exists conversations_user_person_created_at_idx
    on public.conversations (user_id, person_id, created_at desc);
```

また、Supabase Authへの確認は毎回行うと通信回数が増えます。
そこで、検証に成功したトークンはハッシュだけをキーにして、最大30秒だけメモリへ保存します。

長く保存すると、トークンが失効しても古い認証結果を使い続ける時間が増えます。
短くしすぎると、認証APIへの通信が増えます。
今回は30秒という、短いが無駄な問い合わせを減らせる値にしました。

## フロントエンドとの接続で分かったこと

最新のフロントエンドをremoteモードで接続すると、相手の登録、一覧、詳細表示、記憶一覧の取得までは確認できました。

一方、「次の話題を準備」へのリンク先は用意されていましたが、画面自体はまだ実装されておらず、404になりました。

これはバックエンドのデッキ生成APIが壊れているという意味ではありません。
フロントエンドの画面Issueがまだ途中という意味です。

バックエンドのAPIと、フロントエンドの画面の完成度は別々に確認しなくてはいけません。
ここを混ぜると、どちらの担当に問題があるのか分からなくなります。

## 所感

今回分かったのは、セキュリティとパフォーマンスは後から一度に追加するものではない、ということです。

`X-User-ID`は開発の初期段階では便利でした。
しかし、その便利さを本番まで持っていくと認証の穴になります。

また、パフォーマンス対策も、難しいキャッシュを最初に作るより、取得件数を制限し、検索条件に合うインデックスを貼るところから始めた方が分かりやすいです。

次に認証画面が完成したら、実際のSupabase Authログインから取得したaccess tokenでAPIを通し、ユーザーをまたいだデータが見えないことまで確認したいです。
