今回は、AI HACK2026で開発したアプリ「話札」の紹介と、開発中に考えたことをまとめます。

話札は、初対面の人との会話を助けるアプリです。ユーザーの興味や会話の目的をもとに、話し始めるきっかけや、その後の分岐を提案します。

## Authで悩んだところ

話札では、ユーザーのプロフィールや、相手との会話履歴を扱います。

最初は、APIへ`X-User-ID`というヘッダーを送れば、そのユーザーのデータを取得できる仕組みでした。

```text
X-User-ID: 11111111-1111-1111-1111-111111111111
```

開発中に動作を確認するだけなら、この方法はとても便利です。
しかし、ヘッダーにユーザーIDを書いているだけなので、別のUUIDを送れば他人のデータになりすませる可能性があります。

ここで、「ユーザーIDを知っていること」と「そのユーザー本人であること」は違うと気づきました。

そこで、Supabase Authのaccess tokenをAPIへ送り、バックエンド側で検証することにしました。

```http
Authorization: Bearer <access_token>
```

バックエンドは、受け取ったtokenをSupabase Authへ確認します。
検証に成功したときだけ、Supabaseから返されたユーザーIDをデータ検索に使います。

このときに悩んだのは、server-only keyとaccess tokenを混同しないことです。

- server-only keyは、バックエンドがSupabaseへ接続するための秘密情報
- access tokenは、ログインしたユーザーを表す短期のtoken

server-only keyはブラウザへ渡してはいけません。
一方で、access tokenはブラウザからAPIへ送りますが、API側で検証してから使う必要があります。

また、Authを追加すると、APIを呼ぶたびに認証確認が発生します。
これをそのまま繰り返すと、認証の安全性を上げた代わりに、通信回数と待ち時間が増えてしまいます。

今回は、検証に成功したtokenをそのまま保存するのではなく、tokenのハッシュをキーにして、検証結果を最大30秒だけバックエンド内へキャッシュしました。

長くキャッシュすれば速くなりますが、tokenが失効したときに古い認証結果を使う時間も長くなります。
短くしすぎればAuth APIへの問い合わせが増えます。
この安全性と速度のバランスを考えるところが、今回のAuthで特に悩んだところでした。

なお、ログイン画面が完成していないローカル開発では、`AUTH_MODE=legacy`を明示した場合だけ、従来の`X-User-ID`を使えるようにしています。
本番では`AUTH_MODE=jwt`を使い、Bearer tokenがないリクエストを拒否します。

## OrcaRouterの実測値

話札では、会話デッキの生成にOrcaRouterを利用しています。
今回の計測では、次のような表示が出ていました。

```text
Orca: 0.000026
Total tokens: 9.6K
Requests: 6
Average latency: 11.5s
Adoption: 83.3%
Fallback rate: 0%
追加表示の0%: 指標名未提示
```

この数字から、計測した6回ではフォールバックが起きなかったことが分かります。
ただし、Fallback rateが0%だからといって、利用者が速いと感じるとは限りません。

平均レイテンシは11.5秒でした。
会話のきっかけを生成するアプリとしては、ユーザーが待てる時間なのかを考える必要があります。
今後は、許容応答時間とタイムアウト値を決めたうえで、モデルやプロンプト、キャッシュの改善を比較したいです。

また、リクエスト数は6件だけです。
そのため、これは本番性能の結論ではなく、これから比較するための最初のものさしとして扱います。

`0.000026`についても、表示の単位を確認しないまま費用として断定してはいけません。
Adoptionの83.3%や、最後に表示された0%についても、指標名と計算方法を確認してから意味を考える必要があります。

数字は多いほど良いのではなく、何を数えたものなのかを一緒に読むことが大切だと分かりました。

## 所感

今回の開発では、AIに話題を作ってもらう部分だけでなく、ユーザーのデータを誰のものとして扱うか、生成に何秒かかるかまで考える必要がありました。

Authでは、開発中に便利な仕組みを本番へそのまま持ち込まないことが大切でした。
OrcaRouterでは、フォールバック率が0%という良い数字だけで判断せず、平均レイテンシや計測件数も一緒に見る必要がありました。

短い開発期間でも、動けば終わりではなく、「誰のデータを守るのか」「その数字は何を意味するのか」を考えられたことが、今回の大きな学びです。
