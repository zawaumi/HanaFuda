# B7.S パフォーマンス訂正

## 直した点

- `persons`、`conversations`、`person_memories`の一覧取得へ1〜100件の上限を設定
- ユーザー・相手・作成日時を組み合わせた複合インデックスを追加
- 記憶一覧取得をバックエンドAPIへ戻し、最新フロントエンドのGET契約と一致させた
- Supabaseクライアントをプロセス内で再利用
- Supabase Authの検証結果を最大30秒だけキャッシュ
- APIレスポンスをブラウザ・中間キャッシュへ保存しないよう設定

## 制約

ページングのUI契約はまだ確定していないため、現段階では`limit`の上限だけを設けています。100件を超える履歴を画面で扱う段階では、`limit`と`cursor`を組み合わせたページングへ拡張します。

また、認証キャッシュは単一プロセス内の短期キャッシュです。複数インスタンスで共有する必要が出た場合は、Redis等へ移す前に失効反映時間と障害時の挙動を設計します。

## OrcaRouter計測メモ

計測時点で表示されたOrcaRouterの値を、今後の性能比較用のベースラインとして記録します。費用値の単位と、最後の`0%`の指標名はダッシュボード上で確認できていないため、推測で補いません。

| 指標 | 表示値 |
| --- | --- |
| Orcaの値 | `0.000026`（単位未確認） |
| Total tokens | `9.6K` |
| Requests | `6` |
| Average latency | `11.5s` |
| Adoption | `83.3%` |
| Fallback rate | `0%` |
| 追加表示の`0%` | 指標名未提示 |

6リクエストという小さなサンプルなので、現時点では確定的な性能評価ではなく初期ベースラインとして扱います。Fallback rateが`0%`であることは、この計測範囲でフォールバックが発生しなかったことを示します。一方、平均レイテンシ`11.5s`は今後の改善対象として、タイムアウト値や許容応答時間と合わせて評価します。Adoption`83.3%`の定義と、表示上の追加の`0%`の意味は、計測元のダッシュボードで再確認します。
