# 作業手順

1. `resume [ID]` で現在地を読む。初回は project.json の watch（関連ソース・仕様・依存ファイル）、risk_paths（重要領域）、checks（引数列・cwd・timeout_seconds・required）を設定する。上位・既存のプロジェクト指示に合わせる。
2. `start ID --goal ... --accept ... --scope ... --next ... --reason ...` で受入条件を固定。重要変更は `--risk high`。独立作業があれば `--parallel 1` または `2` と理由を記録する。人数は運用上の目安。
3. 必要な範囲だけ調査。単独で十分なら実装へ進む。委譲時は `delegate` に目的・所有範囲・読む範囲・依存作業を記録し、担当に受入条件と検証方法も渡す。実際の起動・停止は利用中のエージェント操作で行う。
4. 所有範囲を重複させない。共有ファイル・Git 統合・共通生成物は統括が直列化。子担当は結果・証拠パス・懸念・次の操作を返す。統括が `child` で記録する。
5. 統合後に `verify ID`。重要変更は非実装者が最終成果物をレビューし、報告書と対象 fingerprint を `review` で記録する。指摘修正後は影響する検証とレビューを更新する。
6. `accept` で各条件の根拠と対象を記録。コード・契約の変更後は受入確認も失効するため再確認する。`checkpoint` で結果・次の操作・未解決事項を保存。`finish` は受入条件、必須検証、必須レビュー、子作業の完了を確認する。

`running` は担当の生存を保証しない。再開時は確認し、不明なら `child --status interrupted` にして成果物を点検する。中断・保留中も書き込み所有を保持する。停止と部分成果を確認し、引き継ぎを記録して旧担当を done にしてから残作業を割り当てる。ロックが残った場合も、書き込み担当が終了したと確認してからロックを取り除く。

検査ツールは保存された証拠を照合する。担当の独立性・受入条件の達成・ログの真正性は統括が実際に確認する。自動起動、モデル切替、強制的なトークン制限は行わない。
